# Operate mode: diagnose

Diagnosis ends with the symptom measured again, not with a plausible explanation. Keep the evidence visible and the failing request reproducible. In the examples below, `RUN` is the absolute path printed by `knowledge.py tmp` at the start of the task; see `01-orient.md`.

## Facts and timeline

- Treat a fact the user states about live state (timeline, what exists, what was deployed) as ground truth. Drop the hypothesis that contradicts it and say which one you dropped. Do not adjust one detail and keep the same line of investigation, because the user's fact already rules it out.
- Start an incident from the timeline: what changed, when, and what the user has already asserted. Ask "what changed after the deploy?" before querying metrics. Do not begin with the metric that supports your favourite theory, because it anchors the investigation.
- Before saying "fixed", reproduce the exact failing request: log the real body and replay it, or use the real client. Re-run the same query that showed the problem and paste the result. Do not test with a request you assembled yourself, because your test can pass while the real one still fails.

Example: "The 5xx was reported after the 14:00 deploy. I dropped the dataset hypothesis and replayed the captured request; it now returns 200."

## Do not hide the error

- Keep stderr on every diagnostic command. Use `set -o pipefail` when piping and print `exit=$?`. Do not use `2>/dev/null` or `|| true` on the command under investigation, because the error is the evidence you need.
- Send long output to a file and read the part you need: `command > "$RUN/out.log" 2>&1; echo exit=$?; tail -50 "$RUN/out.log"`. Do not pipe to `head` or `tail` as the only output, because the pipe replaces the exit code and can hold the pipe open.
- Keep `2>/dev/null` only in existence checks where the error is the answer (`test -f`, `command -v`). Do not make it a habit, because it turns permission errors into "not found".

Example: `vendor-cli status > "$RUN/status.log" 2>&1; echo exit=$?; tail -50 "$RUN/status.log"`.

## Waiting and retries

- Wait on a condition with a timeout: `kubectl wait`, `rollout status`, a vendor "wait" command, or `timeout 60 bash -c 'until curl -fsS URL; do sleep 2; done'`. Do not use a fixed `sleep N` and then read state, because a short wait reads an intermediate state and a long one wastes time.
- Keep one dev server with autoreload running in one background terminal and read that log. Do not start a second instance when the first is slow, because two servers hide which one answered.
- After the same command fails twice, stop and read the full error before a third attempt. Do not vary flags blindly, because each variant creates a new possible cause.

Example: "The service did not answer after 30 s; I read the unit log and found the port already in use" instead of starting it again.

## Real identifiers and real backends

- List real identifiers before writing any ID, slug, environment name, secret key, or variable name: use a list endpoint, `terraform state list`, or `grep` in the repository, then copy one. Do not derive an identifier from a display name, because a wrong slug costs a whole plan, login, or apply cycle.
- Surface the error from the real backend. Do not let a fallback or mock answer when the real service fails, because a plausible answer hides the failure and the next "fix" targets the mock.
- A patch to a model's binary blob is not a fix for a wrong template. Do not keep patching generated bytes; rebuild from the versioned source.

Example: "I listed the projects and copied the slug instead of guessing it from the product name. The gateway returned 500, so I report that error rather than the mock reply."
