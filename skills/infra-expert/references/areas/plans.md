# Area: change plans

A change plan is one Markdown file that a person reads before a change and that an agent applies later. The file lives at `<nearest git root>/.gti/infra-expert/plans/<YYYYMMDD>-<slug>.md` and is committed with the project. Read this file when the change touches more than one target, needs a downtime decision, comes from a CVE or an audit, or when the user asks for a plan. A bring-up request with no plan request goes straight to work as [04-change.md](../operate/04-change.md) says; it does not wait for a plan.

Nothing in a plan is applied by writing the plan. The approval contract below is what releases the change.

## The file

The front matter between the `---` fences is the source of truth. The body below the marker `<!-- plan-body: generated by plan.py render, do not edit below this line -->` is generated by `plan.py render` and is never edited by hand. Edit only the front matter, then render. `check` fails when the body is stale.

The front matter uses a small YAML subset, not a general YAML library. It supports mappings, block lists, list items that are mappings, integers, booleans, inline lists and mappings, and strings written with double quotes. The script writes every string with double quotes so the parser reads back exactly what was written. Standard library only, Python 3.8+.

### Top level fields

| Field | Type | Meaning |
|-------|------|---------|
| `id` | string | `<YYYYMMDD>-<slug>`; the name used when applying |
| `title` | string | Short name of the change |
| `goal` | string | What the change is for, not how it is done |
| `requested_by` | string | Who asked for the change |
| `created` | string | Date in `YYYY-MM-DD` form |
| `status` | enum | `draft`, `proposed`, `approved`, `rejected`, `applying`, `applied`, `rolled-back`, `failed` |
| `scope` | list | Targets the change touches: hosts, services, stacks, or dashboards |
| `risk` | enum | `low`, `medium`, `high` |
| `downtime` | mapping | `kind` is `none` or `needs-decision`; `reason` says why and is never empty |
| `approvals` | list | One entry per decision: `decision`, `who`, `when`, `step`, and optional `reason` |
| `source` | mapping or string | Where the change came from, for example a CVE id and its report path |
| `steps` | list | The ordered or dependent steps below |
| `open_questions` | list | Optional questions that still need an answer |

An approval with an empty `step` is a decision on the whole plan. An approval with a step id is a decision on that step only. Plan approval does not replace a step approval when the step sets `requires_approval: true`.

### Step fields

| Field | Type | Meaning |
|-------|------|---------|
| `id` | string | Unique short id, for example `backup-config` or `s1` |
| `title` | string | One short line |
| `target` | string | Exact host, service, stack, or tool object |
| `method` | enum | `pipeline`, `mcp`, `cli`, `manual`; the value names the exact leaf, tool, or command in `change` |
| `change` | string | Files, commands, or tool call that changes state |
| `rollout` | enum | `rolling`, `blue-green`, `reload`, `no-restart`, `needs-downtime` |
| `backup` | string | What is backed up and where, or `none` |
| `verify` | string | Command or check and the expected result |
| `rollback` | string | How to undo the step, or `none` when nothing changed |
| `depends_on` | list | Step ids that must be `verified` first |
| `requires_approval` | bool | Whether a person must approve this step before it is applied |
| `status` | enum | `pending`, `approved`, `applied`, `verified`, `skipped`, `failed`, `rolled-back` |
| `log` | list | Timestamped entries the applying agent appends with `plan.py step --log` |

Every step needs a non-empty `verify` and `rollback`. Step ids must be unique and every `depends_on` must name a real step. A step with `rollout: needs-downtime` must set `requires_approval: true`. See [assets/templates/plan.example.md](../../assets/templates/plan.example.md) for a complete file that passes `check`.

## When to write a plan

- More than one target changes, or the order matters.
- A step may cause downtime, or a zero-downtime path needs a decision.
- The change comes from a CVE triage or an audit and is not applied in that mode.
- The user asks for a plan, a draft, or a runbook, or says to wait for approval before applying.
- Ask about urgency and availability before accepting a delay or shelving a request, and record the agreed window in the request. An ambiguous "when" is not a reason to rush or to defer indefinitely.

In Autonomous Mode, write the plan and list the apply as pending. Do not approve your own plan or apply a step that needs a person, a downtime window, or a gated action.

Name one owner for communication and a backup for handoff across shifts. When the work depends on a single skilled operator, escalate availability early instead of waiting. Do not schedule a risky change without on-call coverage: flag the missing coverage and name the handoff before the plan is proposed.

## How to fill the fields

Use the operate rules in [04-change.md](../operate/04-change.md) and the project's `conventions.md`.

| Plan field | Where the value comes from |
|------------|----------------------------|
| `scope`, step `target` | The exact targets named after orienting; one entry per host, service, or stack |
| step `method` | The project's provisioning path from `conventions.md`; a method the user names is a requirement, and a missing path is written down, not replaced by a manual one |
| step `change` | The source of truth to change first: a stack leaf, pipeline, config generator, or tool call; not a patch on the live target |
| step `rollout` | A named zero-downtime pattern from the operate rules: rolling by node, blue-green, reload, expand and contract, create before destroy, or pause and resume; `needs-downtime` only when none exists |
| `downtime` | `none` with the pattern in the reason, or `needs-decision` with what goes down, for how long, and the options |
| step `backup` | State the source cannot rebuild: a host config file, database, volume, secret, dashboard, DNS record, or running image; name where it goes |
| step `verify` | A health check loop during the change plus a check after it, with the expected result |
| step `rollback` | The exact path back, including which backups are kept |
| `depends_on` | Steps that must be verified before this one, for example a backup before an upgrade |

Set `risk` from the blast radius and set `status` to `proposed` when the plan is ready for a person. A CVE fix plan carries the CVE id and report path in `source` and keeps every step pending.

## Script commands

All commands take `--help` and use `python3` on macOS and Linux and `python` or `py -3` on Windows. Paths below are relative to `<skill-dir>`.

```bash
python3 scripts/plan/plan.py new --title "Upgrade the edge proxy" --goal "Close the advisory" --start .
python3 scripts/plan/plan.py check <plan.md>
python3 scripts/plan/plan.py render <plan.md>
python3 scripts/plan/plan.py summary <plan.md> --format text
python3 scripts/plan/plan.py approve <plan.md> --by "change owner"
python3 scripts/plan/plan.py approve <plan.md> --step <step-id> --by "change owner"
python3 scripts/plan/plan.py reject <plan.md> --step <step-id> --by "change owner" --reason "no window"
python3 scripts/plan/plan.py step <plan.md> <step-id> --status applied --log "Applied on web-01"
python3 scripts/plan/plan.py list --start .
```

`new` finds the nearest git root from `--start` and creates a draft in `.gti/infra-expert/plans/`. `check` prints one line per problem and exits 1 when any problem is found. `render` rewrites the generated body. `approve` and `reject` record a decision, update the plan or step status, and render. `step` records progress and renders. `list` shows id, status, and title, newest first.

## Approval contract

- Nothing runs before approval. Writing, checking, or summarizing a plan changes only the plan file.
- A plan with `status: approved` gives permission for its steps, except a step that sets `requires_approval: true`; that step needs its own approval.
- A step with `rollout: needs-downtime` always needs its own approval, and a person still decides whether to accept a window, add a second instance first, or defer.
- Rejecting a step sets its status to `skipped`; rejecting the plan sets the plan status to `rejected`. Both keep a dated decision in `approvals`.
- The agent never approves on behalf of a person and never treats an automatic run as approval.

## Apply an approved plan

1. Read the plan and the project rules again. Run `check` and stop on any problem.
2. For each step in order: read `target`, `method`, `change`, `rollout`, `backup`, `verify`, and `rollback`. Take and check the backup before changing state.
3. Set the plan status to `applying` in the front matter, render, and check.
4. Mark the step `applied` with `plan.py step <plan> <id> --status applied --log "..."`. The command refuses when the step needs its own approval and has none, or when a `depends_on` step is not `verified`.
5. Run the change through the named method. Keep the health check loop running during the change.
6. Mark the step `verified` with the check result in `--log`. Only then move to a step that depends on it.
7. On failure, mark the step `failed` or `rolled-back`, keep every backup, set the plan status to `failed` or `rolled-back`, render, and report.
8. When all steps are verified or skipped, set the plan status to `applied`, render, and check. Delete non-database backups after verification and list database backups as pending; see [04-change.md](../operate/04-change.md).

## How a chat bot uses a plan

`summary FILE --format text` prints the title, goal, risk, downtime, one line per step, and what needs a decision. A person reads that text before they decide.

`--format slack` and `--format telegram` print one JSON object with two keys. `message` is the same text. `actions` is a Block Kit `blocks` array for Slack or an `inline_keyboard` array for Telegram. Every action value carries the plan id and, for a step action, the step id only, in this form:

| Action | Value |
|--------|-------|
| Approve plan | `approve-plan:<plan-id>` |
| Reject plan | `reject-plan:<plan-id>` |
| Approve step | `approve-step:<plan-id>:<step-id>` |
| Reject step | `reject-step:<plan-id>:<step-id>` |

There is one approve and one reject button for the plan, and one pair per step with `requires_approval: true`. The bot turns a callback into `plan.py approve` or `plan.py reject`, using the id as `--step` for a step action, and records the sender as `--by`. It posts the new `summary` after the decision. The plan file stays the source of truth; the bot does not keep a second copy of the state.
